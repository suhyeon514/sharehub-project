# 통합 API 검증 실행

## 1. 먼저 검증 모드 선택하기

`backend/scripts/verify_api.py`는 로그인부터 공유·차단·소명·삭제·관리자 이력까지 하나의 문서로 이어지는 API 흐름을 검증한다. **실행 모드는 두 가지이며, 한 번 실행할 때 `--isolated` 또는 `--base-url` 중 하나를 선택한다.**

| 구분 | 격리 모드: `--isolated` | 서버 모드: `--base-url` |
| --- | --- | --- |
| 목적 | 로컬 코드의 API 흐름과 검증 스크립트 확인 | 실행 중인 서버 환경에서 API 통합 동작 확인 |
| 요청 방식 | Flask test client로 앱 내부 호출 | 지정한 서버에 실제 HTTP 요청 |
| DB | 실행마다 생성하는 임시 SQLite | 지정 서버의 `DATABASE_URL`에 설정된 DB |
| 서버 실행 | 불필요 | 백엔드 서버 실행 필요 |
| 계정 | 임시 일반 사용자 2명·관리자 1명 자동 생성 | 대상 DB의 기존 일반 사용자 2명·관리자 1명 준비 |
| 로그인 정보 입력 | 불필요 | 필요. 환경 변수로도 전달 가능 |
| 데이터 영향 | 임시 DB·파일을 종료 시 정리 | 테스트 문서 생성·변경·삭제, 감사·차단·소명 이력 보존 |
| 즉시 파일 cleanup | 실행하지 않도록 mock 처리 | 서버 DELETE 처리에서 시도하지만 완료 여부는 별도 확인 |
| 성공의 의미 | 임시 환경에서 공통 17개 시나리오 통과 | 해당 서버에서 공통 17개 시나리오 통과 |

처음 저장소를 받은 사람은 **격리 모드로 실행을 확인한 뒤**, 테스트 서버와 계정이 준비되면 서버 모드로 진행한다. 
두 모드 모두 브라우저 화면을 조작하지 않는다.

### 공통 실행 준비

별도 표시가 없는 명령은 **저장소 루트**에서 실행한다. 5절에는 `backend/`에서
실행하는 예시도 제공한다. 아래 예시는 Linux/macOS 기준이다.
프로젝트 백엔드 의존성이 설치된 Python 환경이 필요하며 verify 전용 추가 패키지는 없다.
기존 `backend/venv`가 없다면 다음과 같이 준비한다.

```bash
python3 -m venv backend/venv
backend/venv/bin/python -m pip install -r backend/requirements.txt
```

다른 가상 환경을 쓰면 아래 명령의 `backend/venv/bin/python`을 해당 Python 실행 경로로 바꾼다.
Windows에서는 일반적으로 `backend\venv\Scripts\python.exe`를 사용하고, 
`--report`에는 해당 환경에서 쓸 수 있는 경로를 정하거나 옵션을 생략한다.
스크립트는 의존성 설치, 서버 시작, migration 적용을 자동으로 수행하지 않는다.

## 2. 격리 모드: 서버·기존 계정 없이 확인

### 준비와 실행

공통 Python 환경만 준비하면 된다. 실행 중인 서버와 개발 DB 계정은 필요 없다.

```bash
backend/venv/bin/python backend/scripts/verify_api.py --isolated
```

### 진행 과정과 검증 요소

1. 임시 SQLite DB와 업로드 디렉터리를 만든다.
2. 일반 사용자 2명과 관리자 1명, 임의 비밀번호를 자동 생성한다.
3. 로컬 Flask 앱의 로그인 API부터 호출해 **4절의 공통 17개 시나리오**를 실행한다.
4. 로그아웃을 확인하고 JSON·TXT 결과를 저장한다.
5. 임시 DB와 업로드 파일을 정리한다.

인증, 공유 권한, 다운로드 내용, 수정, 검색, 차단, 소명 상태 전이, 삭제 후 API 접근과 이력 보존을 임시 환경에서 검사한다.
설정된 개발 DB에는 접속하지 않는다.

### 검증 범위의 한계

- 실제 HTTP 연결이나 실행 중인 서버의 환경 설정은 확인하지 않는다.
- 모델로 임시 테이블을 생성하므로 migration 적용 여부를 검증하지 않는다.
- SQLite 결과로 MariaDB의 생성 컬럼·FK·잠금·동시성을 증명할 수 없다.
- MariaDB 전용 잠금을 사용하는 즉시 파일 cleanup 함수는 mock 처리한다.
  이는 해당 함수를 실행하지 않도록 대체한다는 뜻이며, cleanup 성공 판정이 아니다.
- JSON의 `mode=isolated`, `immediate_cleanup_mocked=true`로 구분한다.

## 3. 서버 모드: 실행 중인 API와 연결 DB 확인

### 준비와 실행

대상 백엔드가 실행 중이고, 환경 변수·DB 연결·필요한 migration·업로드 디렉터리가 준비되어 있어야 한다.
이 스크립트는 DB 스키마나 기존 계정 역할을 변경하지 않는다.
프런트엔드 서버는 필요 없다.

```bash
backend/venv/bin/python backend/scripts/verify_api.py \
  --base-url http://localhost:8000
```

`localhost:8000`은 예시다. 
실제 테스트 서버의 주소로 바꾸며 `/api`를 붙이지 않는다.
원격 서버에 로그인 정보를 전송할 때는 HTTPS 주소를 사용한다.
로컬 파일을 수정했더라도 실행 중인 서버가 다른 코드를 사용하면 그 서버의 동작을 검증한다.

### 입력할 계정의 의미

**`--base-url` 실행에는 지정한 API 서버가 연결된 DB에 이미 등록되어 있고, 실제로 로그인할 수 있는 서로 다른 세 계정이 필요하다.** 즉석에서 임의의 아이디·비밀번호를 입력해 새 계정을 만드는 방식이 아니다.
스크립트는 입력값으로 `/api/auth/login`을 호출할 뿐 회원가입이나 계정 생성을 하지 않는다.
여기서 DB는 해당 서버의 `DATABASE_URL`로 설정된 DB이며, 개발·테스트 DB일 수 있다.
운영 DB의 계정이어야 한다는 의미는 아니다.

| 입력 순서·역할 | DB에 필요한 조건 | 검증 중 담당하는 동작 |
| --- | --- | --- |
| `owner` | `role=user`인 기존 계정 | 새 문서 업로드, 공유 설정, 소명 제출, 삭제 |
| `receiver` | owner와 다른 `role=user`인 기존 계정 | 공유받은 문서의 조회·다운로드·수정 권한 확인 |
| `admin` | 앞의 두 계정과 다른 `role=admin`인 기존 계정 | 문서 차단, 소명 거절·승인, 관리자 이력 확인 |

`owner`, `receiver`, `admin`은 스크립트에서 사용하는 역할 이름이다.
실제 로그인 아이디가 이 이름과 같을 필요는 없다. 입력하는 아이디는 DB의 `username`이고, 비밀번호는 평소 로그인할 때 사용하는 원래 비밀번호다.
DB의 사용자 숫자 ID나 `password_hash` 값을 입력하는 것이 아니다.
비밀번호 입력은 화면에 표시되지 않는다.

세 계정의 DB 사용자 ID는 모두 달라야 하며 위 역할 조건을 충족해야 한다.
이 시나리오는 비공개 문서를 개별 공유하므로 부서는 같아도 되고 달라도 된다.
계정이 없거나 비밀번호가 틀리면 로그인 검증에서 실패하고, 역할이 맞지 않거나 동일 계정을 재사용하면 계정 조건 검사에서 실패한다.

테스트 계정이 없다면 실행 전에 담당자에게 개발·테스트 DB의 계정 준비를 요청한다.
계정 준비 없이 흐름만 확인하려면 2절의 `--isolated` 실행을 사용한다.
이 모드에서는 스크립트가 임시 DB에 계정과 임의 비밀번호를 자동 생성하므로 사용자가 계정 정보를 입력할 필요가 없다.

계정을 자동 생성하지 않는다. 자동 실행 환경에서는 `VERIFY_OWNER_USERNAME`,
`VERIFY_OWNER_PASSWORD`, `VERIFY_RECEIVER_USERNAME`, `VERIFY_RECEIVER_PASSWORD`,
`VERIFY_ADMIN_USERNAME`, `VERIFY_ADMIN_PASSWORD` 환경 변수를 비밀값 관리 도구로 주입할 수 있다.
인증정보를 코드·결과 문서·명령행 인수에 넣지 않는다.

**이 명령은 지정 서버의 데이터를 변경한다.** 실행마다 `verify-`로 시작하는 임의 제목의 비공개 문서를 새로 만들며 기존 문서 ID를 입력받지 않는다.
성공하면 생성 문서를 소유자 DELETE API로 삭제하고, 차단·소명·감사 이력은 서비스 정책대로 남긴다.
삭제 API가 파일 정리를 시도하지만 HTTP 204만으로 물리 파일 정리 성공을 판정하지 않는다.

실패하면 후속 시나리오를 중단하고 로그인한 세션의 로그아웃을 시도한다.
문서를 자동으로 강제 삭제하거나 차단을 해제하지 않는다. 결과의 `run`, `ids.document`, `ids.block`, `ids.requests`로 생성 데이터와 중단 위치를 확인하고 정상 소명·삭제 절차로 정리한다. 
네트워크 단절 시 서버에서 처리된 요청 결과나 생성 ID를 받지 못할 수 있으므로 `run` 제목으로 확인한다. 로그아웃 실패 시 서버 세션이 만료될 때까지 남을 수 있다.

### 진행 과정과 검증 요소

1. 준비된 세 계정으로 서버 로그인 API를 호출한다.
2. 새 비공개 문서와 파일을 업로드한다.
3. **4절의 공통 17개 시나리오**를 실제 HTTP 요청으로 실행한다.
4. 서버 응답에서 다운로드 내용, 권한 거부, 소명 상태, 삭제 후 이력 등을 확인한다.
5. 로그인 세션의 로그아웃을 시도하고 JSON·TXT 결과를 저장한다.

이 모드는 HTTP 전송과 해당 서버·DB 환경에서의 연속 API 동작을 확인한다.
DB 테이블을 직접 조회해 전체 제약을 검사하거나 동시 요청을 발생시키지는 않는다.
삭제 API의 204 응답도 물리 파일 cleanup 완료를 보장하지 않는다.
JSON의 `mode=http`, `immediate_cleanup_mocked=false`로 구분한다.

## 4. 두 모드에서 공통으로 검증하는 17개 시나리오

아래 검사는 두 모드에서 동일하다. 격리 모드는 임시 SQLite와 로컬 앱,
서버 모드는 실제 HTTP와 대상 서버의 DB를 사용한다.

| ID | 검증 요소 |
| --- | --- |
| AUTH-01 | 세 계정 로그인 성공, 일반 사용자·관리자 역할, 서로 다른 사용자 ID |
| DOC-01 | 비공개 문서 생성, 공유 전 수신자·관리자의 내용 접근 거부 |
| SHARE-01 | view 공유, 조회·댓글 작성 허용, 다운로드·수정 거부 |
| SHARE-02 | download로 변경, 다운로드 바이트 일치, 수정 거부 |
| SHARE-03 | edit로 변경, 다운로드·수정 허용과 수정 내용 재조회, 공유 조회·삭제 거부 |
| SHARE-04 | view로 낮춘 후 다운로드·수정 권한 회수 |
| SEARCH-01 | 공유받은 문서가 수신자 검색 결과에 표시됨 |
| BLOCK-01 | 관리자 차단, 소유자·수신자의 일반 이용 거부 및 검색 제외, 소유자 응답의 내부 근거 제외 |
| APPEAL-01 | 소유자 소명 제출, 대기 요청 중복 제출 거부 |
| APPEAL-05 | 관리자 거절 후 차단 유지·접근 거부, 중복 심사 거부 |
| APPEAL-03 | 새로운 ID로 재소명, 대기 요청 중복 제출 거부 |
| APPEAL-04 | 승인 후 차단 해제·접근 회복, 현재 view 권한 유지, 중복 심사 거부 |
| DEL-01 | 소유자 문서 삭제 204 |
| DEL-02 | 삭제 후 소유자·수신자·관리자의 상세·다운로드·댓글·공유 조회 404, 재삭제 404 |
| ADMIN-HIST-01 | Deleted document appeal history API: 삭제 후 소명 목록·상세 API 응답의 거절·승인 이력, 문서 ID, 심사 불가 상태 확인 |
| LOG-01 | 해당 문서의 `DOCUMENT_DELETE` 감사 로그가 정확히 1건 |
| AUTH-LOGOUT | 로그인한 계정의 로그아웃, 기존 세션으로 재접근 시 401 |

BLOCK-01의 일반 이용 거부는 상세·다운로드·댓글 조회/작성·수정·공유 조회·삭제를 검사한다.
모든 엔드포인트와 권한 조합을 포괄하는 테스트는 아니다.
ADMIN-HIST-01은 API 응답만 확인하며, 관리자 화면의 문구나 브라우저 렌더링은 검증하지 않는다.

## 5. 결과 확인과 보고서 저장

### 5.1 터미널 결과

터미널과 TXT 보고서의 머리말에는 실행 환경과 즉시 cleanup 처리 여부를 표시한다.
격리 모드에서는 다음 설명이 출력된다.

```text
Environment: Temporary SQLite; IDs belong to this isolated run, not the configured server DB.
Immediate cleanup: mocked (not verified).
```

보고서의 `IDs`는 해당 실행의 임시 SQLite에서 생성된 값이다. 실제 서버 DB의
같은 숫자 ID와 연결해서 해석하면 안 된다. 격리 실행이 끝나면 임시 DB는 정리된다.
서버 모드에서는 다음과 같이 구분한다.

```text
Environment: Target HTTP server; IDs belong to its connected DB.
Immediate cleanup: not mocked by verifier; completion not verified.
```

서버 모드의 ID는 대상 서버 DB에 속한다. cleanup을 mock하지 않았다는 설명은
물리 파일 정리가 완료되었다는 뜻이 아니다. 두 모드 모두 JSON의 `not_verified`와
TXT·터미널의 `Scope`에서 cleanup·동시성·브라우저 UI 검증 제외 표시를 유지한다.

각 시나리오의 HTTP 상태와 본문 조건 검사를 모두 마친 뒤 `[PASS]`를 출력한다.
실패한 시나리오는 `[FAIL]`, 그 뒤 의존 시나리오는 `[SKIP]`으로 표시한다.
로그아웃은 앞 단계가 실패해도 로그인된 세션마다 시도하며 별도로 판정한다.
모든 시나리오가 성공하면 `RESULT: PASS`, JSON `passed: true`, 종료 코드 0이다.
실패나 건너뛴 시나리오가 있으면 `RESULT: FAIL`, 종료 코드 1이다.

```text
================================================================
ShareHub Integration Verification
================================================================

[PASS] AUTH-01        Owner / receiver / admin login
[PASS] DOC-01         Document create and private access
[PASS] SHARE-01       View share
... (나머지 시나리오도 각각 출력)
[PASS] LOG-01         DOCUMENT_DELETE exactly once
[PASS] AUTH-LOGOUT    Logout and session invalidation

----------------------------------------------------------------
PASS : 17
FAIL : 0
SKIP : 0
----------------------------------------------------------------
RESULT: PASS
```

### 5.2 기본 저장 위치와 파일 이름

두 모드 모두 결과를 **JSON 상세 보고서 + 같은 이름의 TXT 요약 보고서**로 자동 저장한다.
`--report`를 생략하면 **명령을 실행한 현재 작업 디렉터리의 `verify-results/`** 아래에 시각·임의 접미사로 실행별 파일을 만들고 마지막에 경로를 출력한다.
폴더가 없으면 자동 생성한다. 스크립트 파일의 위치가 아니라 터미널의 실행 위치가 기준이다.

| 명령 실행 위치 | 기본 보고서 저장 위치 |
| --- | --- |
| 저장소 루트 | `verify-results/` |
| 저장소의 `backend/` | `backend/verify-results/` |

예를 들어 `backend/` 디렉터리에서 다음 명령을 실행하면 된다.

```bash
venv/bin/python scripts/verify_api.py --isolated
```

서버 모드도 같은 기준으로 저장한다.

```bash
venv/bin/python scripts/verify_api.py --base-url http://localhost:8000
```

생성 예시: `backend/verify-results/verify-<UTC시각>-<임의접미사>.json`과 `.txt`.
파일 이름의 시각은 UTC 기준이며, 임의 접미사를 붙여 실행별 결과를 구분한다.

```text
backend/
└── verify-results/
    ├── verify-20260915T130637Z-516379.json
    └── verify-20260915T130637Z-516379.txt
```

실행 마지막에 `JSON: ...`, `TEXT: ...`로 저장 경로를 출력한다.
격리 모드의 임시 DB·업로드 파일은 종료 시 정리되지만, 이 결과 보고서는 남는다.
보고서의 기본 저장 위치는 `/tmp`가 아니다.

### 5.3 저장 경로 직접 지정

`--report`로 JSON 파일 경로를 지정하면 기본 경로보다 우선 사용한다.
예를 들어 `backend/`에서 다음 명령을 실행하면
`backend/verify-results/sharehub-api-report.json`과 `.txt`가 생성된다.

```bash
venv/bin/python scripts/verify_api.py \
  --base-url http://localhost:8000 \
  --report verify-results/sharehub-api-report.json
```

상대 경로는 명령 실행 위치를 기준으로 해석하며 절대 경로도 지정할 수 있다.
명시한 동일 경로로 재실행하면 기존 보고서를 덮어쓴다.
실행별 결과를 보관하려면 `--report`를 생략하거나 매번 다른 파일 이름을 지정한다.

### 5.4 보고서 내용과 Git 관리

`verify-results/`는 `.gitignore`에 등록되어 보고서를 실수로 커밋하지 않도록 한다.
다른 폴더를 직접 지정한 경우에는 이 Git 제외 규칙이 적용되지 않을 수 있다.
JSON에는 시나리오 판정·집계·성공한 HTTP 검사·실패 위치·생성 ID·검증 제외 범위를 담고,
토큰·비밀번호·응답 본문은 저장하지 않는다.

시나리오 ID는 이 실행 파일의 집계 단위다. 확정 통합 문서의 같은 ID와
관련되지만 브라우저까지 포함하는 전체 항목의 완료를 뜻하지 않는다.
`SKIP`은 실행 예정인 API 시나리오의 미실행 수이며, 별도 범위인 브라우저·cleanup·
동시성은 집계에 넣지 않고 `not_verified`로 표시한다.

## 6. 전체 검증에서의 위치와 후속 확인

검증 순서는 **기존 unittest·lint/build → 이 API 검증 → 핵심 브라우저 수동 검증**이다.
기존 자동 테스트는 이 파일이 다시 실행하거나 통과로 집계하지 않는다.

| 별도 확인할 영역 | 이 파일만으로 완료 판정하지 않는 이유 |
| --- | --- |
| 전체 권한 행렬 | 팀 권한, 각 목록 제외, 자기 심사·오래된 차단 요청 등은 기존 테스트와 별도 시나리오 필요 |
| MariaDB 제약·동시성 | 순차 API 요청만 실행하며 생성 컬럼·FK·잠금 경쟁을 직접 검증하지 않음 |
| 물리 파일 cleanup | 삭제 응답과 파일 정리 완료는 별개이며 실제 파일·cleanup job 상태 확인 필요 |
| 브라우저 UI | 버튼 노출, 모달·취소·중복 클릭, 화면 이동, 오류 표시, 새로고침은 직접 확인 필요 |

공유할 검증 결과에는 **실행 모드, 실행한 코드 버전, 보고서, 별도 미검증 범위**를
함께 기록한다. 서버 모드에서는 서버가 실행한 코드 버전도 확인한다.
보고서에 모드는 자동 기록되지만 코드 버전은 자동 수집하지 않는다.
이 문서의 PASS 출력은 형식 예시이며, 각 사용자의 실행 성공을 뜻하지 않는다.
